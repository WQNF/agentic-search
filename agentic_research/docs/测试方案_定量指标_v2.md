# 智慧投研 Agent 定量评测方案 v2

> 适用代码：`agentic_research/backend`（FastAPI + LangGraph）
> 评测工装：`agentic_research/backend/tests/eval`
> 本文只定义“怎么测、怎么算、怎么判”，具体数值由工装产出到
> `tests/eval/results/指标回收表.md`。

---

## 0. 摘要

### 0.1 为什么旧结果不能用

旧套件 `backend/tests/test_metrics_battery.py` 的 `metrics_report.json` 给出了
“30/30 成功、100% 完整率”，但同一批 `_e2e_results.json` 里有 14/30 的
`final_status=partial_success`，TSLA 的 `metric_count=0`、`financial_status=partial`。
也就是说，**“成功”是 section 关键词匹配出来的，不是系统质量审核判出来的**。
更严重的是，4/5/6/7–12/15/16 这些指标要么是 0、要么是空、要么分母为 0：

| 指标 | 旧结果 | 真实原因 |
|---|---|---|
| 4/5 字段准确率 | 0.00% / 0.00% | 只比较了 5 只股票 × 25 个键；CN/HK 的扁平中文字典没有映射到英文键；`None==None` 还判对 |
| 6 基线 | 0.00%（5 个比较） | 用 `gross_margin` 这种英文键去中文报告里正则匹配，必然 0 |
| 7–12 工具 | `{}` | 日志路径 `runs/` 相对 cwd 找错；且 `tool_call` 与 `tool_success` 被同时计数，成功率上限只有 50% |
| 15 成本 | ¥0.000000 | token 从未真实采集，字段默认 0 |
| 16 故障 | 0/0 | 故障用例没跑完；且把 `final_status=failed` 的 139 字残报告判成“降级成功” |

所以旧套件不是“结果偏低”，而是**口径不成立**。v2 的目标不是把数字调高，
而是让每个数字都能被复算、被审计、被置信区间约束。

### 0.2 v2 的三条主线

1. **分层口径**：工作流层（能不能跑完）、数据层（字段值对不对）、报告层（用户看到的报告对不对）分开测，不再用一个“成功”混在一起。
2. **期间对齐真值**：字段准确率只和“系统实际使用的那一期”官方数据比，容差 1%；不用一份圆整的、没有期间的 `ground_truth.json`。
3. **全链路真实埋点**：工具按“语义成功”判、LLM 按 callback 的真实 token 计费、延迟按 `perf_counter` 端到端计、故障按契约判。

## 1. 评测目标、对象与边界

### 1.1 目标

回答四个问题，并给出可复算的数字：

- **能用吗**：30 家真实公司，5 个 section 是否非空、有没有 fatal。
- **准吗**：150 个字段（30×5）与官方同期数据是否在 1% 内一致；分市场如何；比单 LLM 基线高多少。
- **稳吗**：工具成功率、10 类故障下降级是否符合契约。
- **值吗**：P50/P95 延迟、单份 token 与成本。

### 1.2 被测对象（真实调用链）

```
POST /api/tasks
  └─ task_runner.run_research_task
       └─ graph.astream(stream_mode="updates")       # Redis checkpointer
            ├─ entity_resolver   entity_resolver.resolve(query)
            ├─ info_collector    create_react_agent + search_web / get_company_profile / get_stock_quote
            ├─ financial_analyzer extract_financial_data(SEC) / get_cn_financial_abstract / get_hk_financial_abstract
            ├─ report_writer     REPORT_SYSTEM_PROMPT + REPORT_HUMAN_TEMPLATE → LLM
            └─ quality_reviewer  7 个标题 + ≥8 个非空指标 → final_status
```

评测工装调用 `build_graph(checkpointer=None).ainvoke(state, config={"callbacks": [...]})`。
它与 `task_runner` 的差异只在编排层（不写 PG/Redis、不做 astream 累积），
5 个节点函数、prompt、工具、模型完全一致。因此本方案的口径是
**“工作流级端到端”**；API 级另做 1 次冒烟，不计入 30 家样本。

### 1.3 不在范围内

- 前端渲染、登录鉴权、任务列表/权限隔离（已有 `test_auth.py` / `test_tasks.py`）。
- PG/Redis 可用性、容器编排、Prometheus 抓取。
- 模型训练/微调；只测当前配置的 `deepseek-flash`。
- 实时行情的绝对正确性（价格每天变）；字段面板刻意避开当日价格类字段。

### 1.4 环境冻结清单（必须写进 manifest）

| 项 | 取值方式 | 示例 |
|---|---|---|
| 代码版本 | `git rev-parse HEAD` | 若未入 git，记录文件树 hash |
| Python / 关键依赖 | `python -V`、`pip freeze` | 3.11.15 / langgraph x.y |

| 并发 | 固定 1（延迟可比） | 1 |

## 3. 旧测试逐条诊断

> 文件：`backend/tests/test_metrics_battery.py`（下称“旧套件”）

### D1. section 判定是关键词包含，不是结构解析

- 旧：`check_core_sections` = `section in report_md and len(report_md.split(section,1)[-1].strip()) > 10`（:356-365）。
- 问题：目录、正文引用、甚至“数据缺失说明”里的“公司概览”都能过；`>10` 字符不要求实义内容。
- 影响：`sections_missing=[]` 恒成立，指标 1/3 虚高。
- v2：按 `##` 标题层级解析，body 去表格符号/占位词后仍需 ≥60 个实义字符。

### D2. fatal 判定把“优雅失败”判成“致命”

- 旧：`has_fatal_error` 对任何 `node=entity_resolver` 的 error 返回 True；`final_status=failed` 也 True（:367-379）。
- 问题：无效代码的预期降级路径被记 fatal；而真正的崩溃（空报告）反而可能漏判。
- v2：fatal = 未捕获异常 / 超时 / 报告 <100 字 / 有效公司实体解析失败；`final_status` 只做分布展示。

### D3. “150 字段”从未被测量

- 旧：`TOTAL_150_FIELDS` 是约 83 个字段**名字**（:191-201），不是 150 个字段**值**；实际只对 `ground_truth` 的 25 键 × 前 5 只股票做比较（:732, :745-756）。
- 影响：`_field_accuracy.json` 是 `3/125`，不是 150。
- v2：150 = 30 家 × 5 个字段，逐家逐字段评分；分母固定，缺测显式标注。

### D4. `None==None` 判对，准确率虚高

- 旧：`check_field_accuracy` 双空返回 True（:443-445）。
- 问题：系统没产出、真值也没有，算“正确”；这与“与官方数据一致”相反。
- v2：真值缺失 → 该字段不计入分母并标 `no_gt`；系统缺失 → 计错且归因 `missing_data`。

### D5. CN/HK 的字段命名空间根本没对上

- 旧：`_build_all_fields` 只读 `financial_raw["standardized"]`（系统从不产出该键）和顶层数值键（中文字段名），而真值是英文键（`revenue` 等）（:675-692）。
- 影响：A/HK 0% 是“键名对不上”，不是“数据错”。
- v2：评分直接读报告层 5 个中英文标签，或数据层 `normalize_financial_data` 的标准键。

### D6. 真值不是官方数据

- 旧：`ground_truth.json` 是圆整值（`market_cap: 3500000000000`、`pe: 33.5`、`price: 240.0`），没有 `period_end`、没有 `source`，还有拼写错误 `total_aliabilities`（09618.HK）。
- 影响：即使字段对上了，也无法判断“和哪一期官方数据一致”。
- v2：真值 CSV 必须有 `period_end / currency / source / source_url / source_tier / verified`。

### D7. 基线不可比

- 旧：只跑 `stocks[:3]`（:817）；用 `re.search(rf'{field}.*?([\d,.]+)')` 在中文报告里找 `gross_margin`（:844-853）。
- 影响：只得到 5 个比较、0%——不是模型能力，是解析器找不到键。
- v2：同 30 家、同报告 prompt、同报告层解析器；空工具数据；输出 150 字段准确率 + 弃答率。

### D8. 工具成功率分母翻倍

- 旧：`parse_log_tool_calls` 把每个带 `extra.tool` 的事件都算一次调用，`tool_call` 和 `tool_success` 各加 1（:408-427）。
- 影响：即使 100% 成功，成功率也 ≤50%。
- v2：在工具函数边界 wrapper，一次调用只记一次；`semantic_ok` 单独判。

### D9. SEC/akshare/yfinance 的调用根本没记日志

- 旧：`financial_analyzer_node` 直接调用工具，没有 `run_log(..., tool=...)`（`nodes.py:355-395`），只有 `node_start/success`。
- 影响：指标 9–12 无法从日志算。
- v2：wrapper 覆盖 6 个工具函数，provider 维度聚合。

### D10. 故障判定把失败当成功

- 旧：`degradation_ok = report_len>50 and final_status!="pending"`（:1050-1053）。
- 证据：`_fault_results.json` 里 `entity_timeout` / `entity_invalid` 都是 `final_status=failed`、`report_len=139`，却 `degradation_ok=true`。
- v2：每类故障有契约（不崩溃 + 报告存在 + 明确说明 + 不编造财务数字）；`failed` 不再自动算成功。

### D11. LLM 故障 patch 打错目标

- 旧：`monkeypatch.setattr("app.core.llm.get_llm", ...)`（:1162-1164）。
- 但 `nodes.py:13` 是 `from app.core.llm import get_llm`，节点里已经绑定的是旧引用；patch 模块属性不会改节点里的名字。
- 影响：`llm_timeout` 用例实际没注入，却可能因为其他失败被记成“通过/失败”。
- v2：patch `app.graph.nodes.get_llm` / `app.graph.nodes.create_react_agent`。

### D12. 延迟/成本是估算，不是采集

- 旧：`EST_INPUT_TOKENS_PER_CALL=8000`、`report_len*1.5`、硬编码 ¥1/¥2（:117-122, :381-392）。
- 证据：`_e2e_results.json` 每条 `estimated_cost_rmb: 0.0`；`metrics_report.json` 平均成本 ¥0.000000。
- v2：LangChain callback 读真实 `usage_metadata`；`prices.json` 由运行日账单填写，未填只报 token。

### D13. 缺失 17–21 项

旧套件只覆盖 16 项；没有人工评分、没有错误分类。v2 补齐 rubric、双人盲评、错误分类表。

### D14. 测试入口与生产入口不一致

旧套件 `graph.ainvoke` + `checkpointer=None`；生产是 `task_runner` + `astream` + Redis checkpointer。
状态累积/最终状态归一化可能不同。v2 声明“工作流级”，并对 API 层另做冒烟。

### 4.2 指标 1 / 3：成功与完整

**5 个核心 section**：公司概览、业务与行业、近期新闻与舆情、财务分析、风险提示。

**“非空”判定**（`tests/eval/text.py:is_substantive`）：

1. 必须是 `##`（1–3 级）标题，标题文字匹配别名（不是正文里出现关键词）；
2. body 去掉表格符号、`#`、`*`、空白后，仍需 ≥60 个字符；
3. body 去掉「数据缺失 / 暂无 / 未披露 / 不适用 / N/A / 无法获取」后，仍需有中英文实义字符。

**fatal**（只用于指标 1）：

- 未捕获异常 / 超时（>600s）；
- 报告 <100 字；
- **有效公司**实体解析失败（无效代码走指标 2，不算这里）。

**不把 `final_status` 当成功**：`quality_reviewer` 只认 7 个标题 + ≥8 个指标，和内容质量弱相关；`final_status` 只作为分布展示（`metrics["1"].final_status_dist`）。

**指标 1 与 3 的关系**：指标 3 只看完整，指标 1 = 完整 ∧ 无 fatal，所以正常应有 `指标1 ≤ 指标3`。

### 4.3 指标 4 / 5：150 字段

**150 = 30 家 × 5 个字段**。字段面板：

| 字段 | 定义 | 美股真值 | A 股真值 | 港股真值 |
|---|---|---|---|---|
| `revenue` | 营业收入（合并） | SEC `Revenues` / `RevenueFromContractWithCustomerExcludingAssessedTax` | 新浪 `营业总收入` | 东财 `营业额` |
| `net_income` | 归母净利润 | SEC `NetIncomeLoss` | 新浪 `归属于母公司所有者的净利润` | 东财/港报表 `股东应占溢利` |
| `gross_margin` | `(revenue - 营业成本) / revenue` | SEC `GrossProfit / revenue` | 新浪 `(营业总收入-营业成本)/营业总收入` | 东财 `毛利/营业额` |
| `net_margin` | `net_income / revenue` | 计算 | 计算 | 计算 |
| `operating_margin` | `营业利润 / revenue` | SEC `OperatingIncomeLoss / revenue` | 新浪 `营业利润 / 营业总收入` | 东财 `经营溢利 / 营业额` |

**为什么是这 5 个**：

- 都是报告 prompt 要求/报告实际披露的核心指标，报告层可解析；
- 三地都能从标准报表得到，不依赖当日股价；
- **不把 ROE 放进 150**：官方 ROE 有加权平均/期末权益/年化多种口径，1% 容差下无法唯一判定。ROE 当前不进入 21 项（可作为可选诊断字段另行解析）。若项目方坚持 ROE，改 `config.FIELD_PANEL` 即可，但必须同时改真值公式并写进 manifest。

**容差**：

- 一般字段：`|actual-expected| / |expected| ≤ 1%`；
- 比率：再加绝对下限 `0.0005`（0.05 个百分点），避免极小分母把 0.0001 的差判错；
- 币种/单位不换算：真值按报告币种（USD/CNY/HKD）记账；报告若写“亿美元/亿元”，解析时乘回基础单位；币种不一致直接判错并归因 `unit_currency`。

**报告层 vs 数据层**：

- 指标 4/6 用**报告层**（用户看到的 Markdown 财务表），这样和基线可比；
- 数据层（`normalize_financial_data` 的标准键）作为诊断输出，不替代指标 4；
- 报告层解析不确定的值带 `needs_review`，人工复核后再进最终表（记录复核人）。

**分母规则**：

- 全量跑满 30 家 → 分母 150；
- 试点/缺测 → 分母 = 已评字段数，表格显式写“已测 N/150（未完成）”，不能把 3/5 写成 3/150。

### 4.4 指标 6：单 LLM 基线

- 30 家，同一 `REPORT_SYSTEM_PROMPT` / `REPORT_HUMAN_TEMPLATE`；
- `profile={}`、`news=[]`、`financial_raw_summary={}`、`metrics={}`，只给公司名/代码/市场；
- 同模型、同 temperature（0.3）、同 max_tokens（16000）、**不挂任何工具**；
- 用与指标 4 完全相同的解析器与真值；
- 结果同时报告：
  - 字段准确率（正确/150）；
  - 弃答率（报告明确写“数据缺失/无法获取”的字段占比）；
  - 与系统报告层的配对 McNemar 检验（同一公司同一字段，系统对/基线错 vs 系统错/基线对）。

### 4.5 指标 7–12：工具成功率

**计数点**：工具函数入口/出口 wrapper（`tests/eval/instrument.py`），一次调用只记一次。
tenacity 内部重试算同一次调用，另记 `duration`；重试次数后续可从日志补。

**语义成功**（不是“没抛异常”）：

| 工具 | 成功条件 |

| `search_web` | 返回 list，且至少 1 条有 title 或 url |
| `get_company_profile` | dict，且 name/ticker/industry/description/website/employees/country 中 ≥3 个非空 |
| `get_stock_quote` | dict，`price` 为数字且 >0 |
| `extract_financial_data` / `fetch_sec_filings` | 三大报表中 ≥2 个有 ≥3 条记录（filings：≥1 条） |
| `get_cn_financial_abstract` / `get_hk_financial_abstract` | dict ≥3 键，且至少 1 个数值非空/非 NaN |

**provider 归属**（按实际 provider，不按工具名）：

| 指标 | provider 标签 | 说明 |
|---|---|---|
| 8 Tavily | `search:tavily` | 当前 `.env` 是 serper → 0 次调用，记 N/A；另报 serper |
| 9 SEC EDGAR | `sec_edgar` | `extract_financial_data`（+ `fetch_sec_filings` 如启用） |

**样本量**：指标 7–12 的口径是“全部调用”，不固定 30；若某 provider 调用数 <10，另做 10 次定向探测并在备注标“定向探测，非端到端样本”。

### 4.6 指标 13–15：延迟与成本

**延迟**：

- 端到端：`perf_counter` 包住 `graph.ainvoke`，包含 5 个节点、所有工具和 LLM，不含评分/落盘；
- 30 家全量，顺序执行（并发=1），避免互相抢代理/限流；
- 先跑 3 次预热（每家市场 1 次）不计入；正式 30 次计入；
- P50/P95 用线性插值；95% CI 用 bootstrap（5000 次，固定 seed=42）；
- 同时报告“仅成功样本”的 P50/P95，避免失败快/慢把分布带偏；
- 超时（>600s）记截尾值并标注，不静默丢弃。

**成本**：

- 从 LangChain callback 的 `usage_metadata` / `llm_output.token_usage` 取真实
  `prompt_tokens`、`completion_tokens`、`cached_tokens`、`reasoning_tokens`；
- `reasoning_tokens` 按输出计费（`deepseek-flash` 是推理模型）；
- 单价写 `tests/eval/results/prices.json`，必须记录 `as_of` 与来源（账单/价目页）；
- 单份成本 = 总成本 / 30；同时报总 tokens、cache 命中 tokens；
- **单价未配置时只报 token，成本列写“待单价”**，不用估算值冒充。

### 4.8 指标 17–20：人工评分

**抽样**：从 30 份报告中分层抽 10 份：US 4 / CN 3 / HK 3；其中至少 2 份是 partial/降级报告；固定随机种子。

**评分维度（1–5，整数）与锚点**：

| 维度 | 1 | 3 | 5 |
|---|---|---|---|
| 完整性 | 缺 2+ 个核心 section 或关键字段大面积缺失 | 5 个 section 都有，但财务/新闻其一明显单薄 | 5 个 section 充实；关键指标、新闻、风险、结论齐全 |
| 事实一致性 | 多处数值与官方/输入矛盾，或明显编造 | 大部分可核对，个别口径/期间不一致 | 抽查 5 个数值全部与官方/输入一致；无编造；期间/币种标注清楚 |
| 结构 | 标题层级混乱、表格错位、难以阅读 | 7 章齐全、有表格，但逻辑/排版一般 | 层级清晰、表格规范、论证连贯、附录完整 |
| 可 action 性 | 只有泛泛而谈，没有结论/风险/催化 | 有结论和风险，但缺条件/仓位/投资者适配 | 结论明确、给出适用投资者/关键变量/风险触发条件 |

**流程**：

- 2 名评分者独立、盲评（隐藏系统/基线、隐藏彼此分数）；
- 先各自打分，再讨论分歧 >1 分的项，但**保留原始分**；
- 报告 `mean`、`SD`、两位评分者“差值 ≤1”的比例；样本 ≥10 时可补 ICC(2,1)；
- 评分表：`tests/eval/results/human_scores.csv`（列：`report_id, rater, completeness, factuality, structure, actionability, notes`）。

### 4.9 指标 21：Top 3 错误类型

固定分类（`config.ERROR_TAXONOMY`）：

| 代码 | 含义 | 自动判定线索 |
|---|---|---|
| `tool_timeout` | 工具/LLM 超时 | error 含 timeout / TimeoutError |
| `tool_error` | HTTP/解析异常 | 工具 `status=error` |
| `entity_resolution` | 实体解析错/未解析 | 指标 2 失败、entity failed |
| `field_mapping` | 原始字段没映射到标准键 | 系统缺失但 raw 有值 |
| `period_mismatch` | 期间错（YTD vs FY、上年 vs 本年） | 数值接近但不等，且 raw 期间≠真值期间 |
| `unit_currency` | 亿/万/千、USD/HKD/CNY | 数值差 1e2/1e4/1e8，或币种不一致 |
| `missing_data` | 数据源确实没有 | 报告字段缺失且 raw 无对应值 |
| `llm_hallucination` | 报告数字不在输入里 | 报告值无法从 raw/metrics 复现 |
| `report_format` | section 缺失/表格坏 | 指标 1/3 失败 |
| `numeric_calc` | 公式/派生算错 | 原始字段对、比率错 |

每个错误字段/失败任务给**一个主类**；抽 20% 双人复核一致性。Top 3 按次数排序，次数相同按严重度（entity_resolution > unit_currency > ...）。

## 6. 真值协议

### 6.1 期间对齐（v2 最关键的一条）

系统实际使用的期间不是统一的：

- US：`extract_financial_data` 取最新 10-K（FY）；
- CN：`stock_financial_abstract` 取最新一期（可能是半年报/季报，2026-06-30 这类 YTD）；
- HK：东财“年度”报表，但 `FISCAL_YEAR` 列是 `"12-31"`，必须按 `REPORT_DATE` 取最新。

**规则**：真值取“系统同一期”的官方数据，并在 CSV 里写 `period_end`。
不能拿 FY2025 年报去比系统 2026H1 的 YTD 数据；那是期间错，不是字段错。
评分时若发现数值接近但不等，先查 `period_end`，归因 `period_mismatch`。

### 6.2 来源分层

| tier | 含义 | 可用于最终 1% 准确率？ |
|---|---|---|
| `official_filing` | SEC XBRL / 交易所年报 PDF / 公司公告 | 是 |
| `vendor_crosschecked` | 两个独立供应商一致（差 ≤1%） | 是，备注供应商 |
| `vendor` | 单一供应商（如东财/新浪） | 只用于预跑，表内标“参考值口径” |
| `missing` | 取不到 | 不计入分母 |

当前工装：

- US：`official_filing`（SEC companyfacts，按 10-K accession 取同期值）；
- CN：`vendor`（新浪财务报表，与系统使用的同花顺摘要独立）；
- HK：`vendor`（东财港股报表，与系统同源；最终需用 HKEX 年报 PDF 复核 20%）。

**最终交付前**：至少对 30 个字段（A/HK 各 10、US 10）做官方 PDF/公告复核，
把 `verified` 置 `True`；未复核的字段在表内标“参考值口径”。

### 6.3 单位/币种

- 金额统一为报告币种的基础单位（元/美元/港元）；
- 比率用小数（0.469，不是 46.9）；
- 真值 CSV 记录 `currency`；报告若写“亿美元/亿元/万港元”，解析时乘回；
- 不做汇率换算；币种不一致判 `unit_currency`。

### 6.4 容差

见 4.3。比率额外 0.0005 绝对下限；金额不加绝对下限（避免 0 附近误判）。

### 6.5 双人核验

- 真值由 1 人录入/自动抓取，另 1 人抽查 ≥20%；
- 抽查项：代码、期间、币种、数值、来源 URL；
- 差异 >1% 的字段回到原始公告重取；
- 记录 `verified_by` / `verified_at`（CSV 可加列）。

### 6.6 为什么弃用旧 `ground_truth.json`

- 圆整值（`market_cap=3.5e12`、`price=240`）不是某一期官方值；
- 无 `period_end`、无 `source`；
- 键名与系统输出不一致（`total_aliabilities` 拼写错误）；
- 30×25=750 个值，但没有一个能追溯到公告。

## 7. 测量与埋点

### 7.1 工作流层

- `perf_counter` 包住 `graph.ainvoke`；记录 `duration_s`；
- 记录 5 个 `*_status`、`final_status`、`errors`、`steps`（节点耗时）；
- 每次运行保存：`results/runs/<run_id>/report.md`、`result.json`、`metrics.json`；
- `runs.jsonl` 追加一行，支持断点续跑（按 symbol 去重）。

### 7.2 工具层

- `tests/eval/instrument.py` 在 `app.graph.nodes` 上包 6 个工具函数；
- 记录 `tool / provider / status / semantic_ok / error_type / duration_ms / result_summary`；
- **注意**：`get_cn_*` / `get_hk_*` 吞异常，必须 `semantic_ok` 判空。

### 7.3 LLM 层

- `graph.ainvoke(..., config={"callbacks":[handler]})`，`handler.on_llm_end` 读
  `llm_output.token_usage` 或 `usage_metadata`；
- 记录 `prompt/completion/cached/reasoning/total tokens`；
- 不估算、不用 `report_len*1.5`。

### 7.4 报告层

- 解析器：`tests/eval/text.py`；
- 标题解析 → 5 个 section；
- 字段解析：标签优先级（长标签优先）、表格单元格内取第一个数、单位乘数、`%` 转小数；
- 解析不确定（`unit_missing` / `percent_without_sign`）标 `needs_review`，人工复核；
- **报告产物坑**：`05_report.md` 是 JSON 转义串；评测用内存态报告，或 `json.loads` 解码后再解析。
  这一点同时是生产缺陷（API 返回的 `report_markdown` 会是一行转义串），建议另开修复单。

### 7.5 运行隔离

- 节点产物写到 `tests/eval/results/app_runs/`，不污染线上 `runs/`；
- 结果目录：`tests/eval/results/{runs,runs_baseline,runs_faults,app_runs}`；
- 每轮生成 `manifest.json`（代码版本、依赖、provider、价格、开始/结束时间）；
- 断点续跑：`runs.jsonl` / `baseline.jsonl` / `faults.jsonl` / `invalid.jsonl` 按 symbol/scenario 去重。

P3 人工评分必须用 P2 的报告，不能边跑边评。

## 9. 统计方法

| 场景 | 方法 | 说明 |
|---|---|---|
| 比例（指标 1/2/3/4/6/16） | Wilson 95% CI | n=3/10 时区间很宽，表内同时给 count/total |
| P50/P95 | 线性插值 + bootstrap 5000 次 | 固定 seed=42；同时报成功样本 |
| 系统 vs 基线 | McNemar 精确检验 | 同一公司同一字段配对；报告 b/c 与 p 值 |
| 人工评分一致性 | 差值 ≤1 比例；n≥10 可补 ICC(2,1) | 保留原始分，不只报平均 |
| 分市场 | 各 50，分别给 CI | 不把 A/HK/US 混成一个数掩盖差异 |
| 多重比较 | 不做 p-hacking；只报预设指标 | 21 项里探索性比较标注“探索性” |

**不要做的事**：

- 不给没有分母的百分比；
- 不把 N/A 写成 0%；
- 不用“平均成功率”掩盖某个市场 0%；
- 不删失败样本（失败也是结果）。

## 11. 风险与限制

| 风险 | 影响 | 缓解 |
|---|---|---|
| 期间不对齐 | 字段准确率被系统性低估/高估 | 真值记录 `period_end`；先查期间再判错 |
| 供应商数据≠官方 | A/HK 的“准确率”其实是“与供应商一致率” | `source_tier`；20% 官方 PDF 复核；未复核标“参考值口径” |
| 报告层解析漏值 | 准确率低估 | `needs_review` + 人工复核；解析器 golden set ≥95% |
| 模型/网络非确定 | 延迟、成功率波动 | 固定并发/窗口；记录 provider 状态；关键指标可重复 3 次 |
| 30 家样本小 | CI 宽 | 报 CI；不外推总体；分市场分别看 |
| CN/HK 结构性缺口 | 字段准确率被数据源限制 | 同时报“数据层可用率”；把缺口写成待修复项，不混入模型能力评价 |
| 人工评分主观 | 17–20 不稳 | 双人盲评、锚点、保留原始分、报一致性 |
| 单价未知 | 成本缺失 | 只报 token；单价由账单填；不估算 |

**已知结构性缺口（当前代码）**：

1. CN/HK 公司概况不支持 → `profile_status=partial` 是必然；
2. CN/HK 行情 provider=eastmoney 不支持 → 行情调用必失败；
3. HK 财务只有利润表，没有资产负债表 → ROE/资产负债率类字段不可得（本方案已把 ROE 移出 150）；
4. HK 东财 `FISCAL_YEAR` 是 `"12-31"`，现有 `get_hk_financial_abstract` 按它取数会取错年份；
5. 报告产物 `05_report.md` 被 JSON 转义，API/下载返回的不是 Markdown；
6. `CNAdapter` 对任意 6 位代码返回 Entity（无效代码 999999.SH 会被“解析成功”）。

这些不是测试口径能修的；它们本身就是 v2 要暴露的结论。

## 14. 附：一句话回答“旧结果怎么修”

不是修 `test_metrics_battery.py` 的几个断言，而是：

1. 换真值（期间对齐、可追溯）；

5. 换统计（分母、CI、N/A）；

这六件事做完，旧套件的 100% 会自然回落到它该有的位置。

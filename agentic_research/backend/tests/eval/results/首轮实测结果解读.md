## 2. 关键发现与证据

### F1. 港股 0/50：取错年份 + 不统一单位（最严重）

`tools/cn_hk_financials.py:139-157` 的 `get_hk_financial_abstract`：

```python
latest_year = df['FISCAL_YEAR'].max()
year_data = df[df['FISCAL_YEAR'] == latest_year]
...
result[row['STD_ITEM_NAME']] = row['AMOUNT']   # 后写覆盖前写
```

`FISCAL_YEAR` 列的值是 `"12-31"`（不是年份），所以 `year_data` 包含所有年度；
循环最后写入的是**最旧一期**，且没有统一“万元/元”单位。

证据：

- `00700.HK` 报告写“营业额 46,639,000（原始单位）”，GT（东财 FY2025）是 **743,689,000,000**；
- `09988.HK` 报告营收 158,273,000,000，GT 1,023,670,000,000（季度/旧年）；
- `01024.HK` 报告营收 1,428，GT 142,776,000,000（少 1e8）；
- 10 家港股 × 5 字段 = 50 个字段全部错。

这不是模型问题：报告甚至主动提示“原始数据单位不一致”。**修复点在工具层**：
按 `REPORT_DATE` 取最新一期；用报表 `币种/单位` 归一；港股补资产负债表（ROE 类字段）。

### F2. 美股 60%：10-K 取到旧列（GOOGL / AMZN）

`tools/sec_financials.py:114-131` 的 `extract_data`：

```python
first_val = next(iter(vals.values()), None)
```

`values` 是多列（多年）字典，`next(iter(...))` 取到的是**旧列**，不是最新列。

证据：

- `GOOGL`：`filing_info.period_of_report=2025-12-31`，但 `Revenues=307,394,000,000`
  （FY2023），报告自己标注“财务数据口径：FY2023”；GT FY2025 是 402,836,000,000；
- `AMZN`：营收 574,785,000,000（FY2023），GT FY2025 716,924,000,000；
- 两家共 10 个字段错，全部归因 `period_mismatch`。

修复：按 `filing_info.period_of_report` 选列，或直接读 `companyfacts` 的同期 `accn`。

### F3. TSLA 5 个字段全缺失：edgartools 抓到 10-K/A

报错原文：

```
Failed to resolve BalanceSheet for Tesla, Inc. ... No matching statements found.
Filing(... form='10-K/A' ...) is an amended filing and may not contain full XBRL data
```

`get_filings(form="10-K").head(1)` 把 10-K/A 当成最新 10-K。修复：
`get_filings(form="10-K", amendments=False)`，或优先原始 10-K。

### F4. WMT / KO 净利润缺失：报告输入被截断到 2000 字符

`graph/nodes.py:479`：

```python
financial_raw_summary = json.dumps(financial_raw, ...)[:2000]
```

利润表在“税前利润”处被截断，净利润没进 prompt；报告只能写“数据缺失”。
证据：WMT 报告明确写“利润表在税前利润一行处被截断”；KO 同样。
这不是模型不写，是**上下文构造 bug**。修复：不要把原始 JSON 截断，改为结构化摘要
（revenue/net_income/毛利率/净利率/营业利润率等 10 个关键字段）。

### F5. A 股 84%：口径差异 + 单位漏写

- `600519.SH / 000858.SZ / 002415.SZ / 600887.SH` 的 `net_margin` 错：
  系统用**合并净利润**（含少数股东）算净利率，本方案用**归母净利润**；
  例如 600519：50.75% vs 48.24%。这是口径不一致，不是算错。
- `600900.SH` 营收/净利润写成 `379.29 / 147.56` 没写“亿元”，解析按元处理 → 少 1e8。
- `000333.SZ` 毛利率 25.26% vs 25.54%，差 1.1%，属于边界误差。

**结论**：A 股的数据层基本可用（84%），剩余主要是口径和单位披露；
如果项目方接受“合并净利润”口径，应在字段定义里写清楚并重算真值。

### F6. 单 LLM 基线 0%：不是模型差，是“没有数据就诚实弃答”

- 30 份基线报告，148/150 个字段写“数据缺失/无法获取”，没有编造；
- 严格按“与真值一致”计，0/150；
- 这恰好证明工具链的价值：有工具 48%，无工具 0%（但弃答率 98.7%）。
- 如果只看“不编造”，基线很好；如果看“字段覆盖”，基线为 0。两个数都要报。

### F7. 工具成功率 89%：被 profile / 行情拖累

| provider | 成功/调用 | 说明 |
|---|---|---|
| serper（搜索） | 315/316 = 99.7% | 基本稳定 |
| SEC EDGAR | 9/10 = 90% | TSLA 10-K/A |
| akshare | 20/20 = 100% | 只判非空；港股取错期仍算成功 |
| company_profile | 11/32 = 34.4% | CN/HK 不支持；US SEC/Yahoo 偶发 |
| eastmoney（行情） | 8/30 = 26.7% | CN/HK secid 构造只支持美股 |

`get_company_profile` 只支持 US（`company_profile.py:23-35`），CN/HK 必失败；
`get_stock_quote` 的 eastmoney 分支只构造美股 secid（`stock_quote.py:118-172`），CN/HK 必失败。
这两项是“结构性失败”，不是随机抖动。

### F8. 故障 9/10：LLM 超时的 fallback 报告太薄

`llm_timeout` 的 fallback 报告 795 字，7 个标题都有，但：

- 公司概览 72 字（大量“数据缺失”）
- 业务与行业 39 字
- 风险提示 15 字

按“5 个 section 有实义内容”判失败。旧套件会因为 `report_len>50` 把它判成功。
修复：fallback 模板要么写足 5 个 section 的最小内容，要么把状态明确标为 failed 并返回错误页，
不要给用户一份“看起来完整、其实没有内容”的报告。

### F9. 无效代码 2/3 严格、3/3 宽松：999999.SH 的内部状态误报

- `ZZZZZZ`、`88888.HK`：实体失败、报告明确说明无效，严格通过；
- `999999.SH`：`CNAdapter` 对任意 6 位代码返回 Entity（`cn_adapter.py:180-182`），
  `entity_status=success`；`get_cn_financial_abstract` 返回 `{}` 但 `financial_status=success`；
  报告本身却正确写明“无法对应任何真实上市公司”，没有编造。
- 所以：**用户可见的降级是成功的（3/3）**，但**内部状态是错的（2/3 严格）**。
  这正是要暴露的：状态字段不能作为唯一真相，报告内容也要校验。

### F10. 指标 1 100% ≠ 质量 100%

- 指标 1（流程成功）30/30；
- `final_status=success` 只有 13/30，17 份 partial；
- 字段准确率 48%。

这就是为什么 v2 要把“流程成功 / 报告完整 / 字段准确 / 质量成功”分开。
只报 30/30 会重蹈旧套件的覆辙。

## 3. 结果怎么读（给验收/汇报用）

建议按三层汇报，不要只报一个数：

1. **流程层**：30/30 跑完，5 个 section 都有，P50 75.8s、P95 126.4s；
2. **数据层**：150 字段 48.0%；A 84%、US 60%、HK 0%；单 LLM 0%（弃答 148/150）；
3. **质量层**：`final_status=success` 13/30；故障 9/10；人工评分待做。

一句话对外表述：

> 系统可以稳定产出结构完整的报告（30/30），端到端 P50 约 76 秒；
> 但在 1% 容差下，150 个财务字段只有 48% 与同期参考值一致，
> 主要瓶颈是港股财务取错期间/单位与美股 10-K 取旧列，而不是报告写作能力。
> 接入工具后字段准确率从单 LLM 基线的 0%（弃答 98.7%）提升到 48%。

## 5. 还缺什么

1. **单价**：`results/prices.json` 填 input/output/cached 单价（运行日账单），
   重跑 `aggregate` 即可得到单份成本。
   当前 tokens：754,211 in / 321,032 out / 514,048 cache（30 份）。
   *示例*：若按 ¥1/¥1/¥2 每百万 token 估算，约 ¥0.047/份；这只是示例，不是结果。
2. **人工评分**：按 `results/human_rubric.md` 抽 10 份、2 人盲评，填 `human_scores.csv`，重跑 `aggregate`。
3. **官方真值复核**：CN/HK 当前是 vendor 参考值；最终交付前用交易所年报 PDF 复核 ≥20%，
   把 `verified` 改 `True`。US 是 SEC XBRL（official）。
4. **可复现性**：记录代码 commit / 依赖版本 / 运行日 / provider；`metrics.json.meta.environment` 已有部分。
